ClosedLoop V3.4 RC2.2 闭环自动化教程中心

完全零基础版：按章节阅读，适合刚接触电脑不久的用户。

这是可直接部署的静态网站，不需要数据库或后端程序。

先记住这 8 句话

正常时，是“ChatGPT 决策端”和“CodeBuddy”来回工作：决策端负责想下一步，CodeBuddy 负责真的操作电脑。

  1. 需求润色端主要在项目开始时用来把你的话整理清楚；它不负责长期执行项目。
  2. 异常修复端平时待机。只有闭环真的卡住，而且 CodeBuddy 自己的普通恢复也解决不了时，才介入。
  3. CodeBuddy 一轮工作结束，不等于整个项目结束。大型任务可以一轮一轮做很多次。
  4. 正常运行时，你不需要反复输入“继续”“继续闭环执行”。RC2.2 的目标就是让系统自己接力。
  5. 看到 ChatGPT 页面空白、假“正在思考”、连接中断、发送超时，不要自己乱点重试或重复发送。
  6. 真正需要你本人出手的，主要是登录、验证码、2FA、电脑重启后自动链路没恢复、长期断网、人工测试等真实人工边界。
  7. 如果你不知道发生了什么：不要猜、不要重发、不要重做。保留现场，按“人工恢复桥”把 CodeBuddy 最后内容和你看到的真实情况交给修复端。
最重要的一句话：正常时“决策端 ↔ CodeBuddy”；异常时“CodeBuddy ↔ 修复端”；修好以后必须回到原主闭环。

这套 ClosedLoop 到底是什么

你可以把它想成一个“会自己记录进度、会分轮工作、出问题会尝试自救”的自动化项目班组。

角色把它想成负责什么
需求润色端需求整理员把你说的话整理成清楚、可确认的需求包。
ChatGPT 决策端项目经理研究、判断、审核上一轮结果、决定下一轮做什么。
CodeBuddy实际操作员读文件、改文件、操作浏览器、验证真实结果、汇报给决策端。
ChatGPT 异常修复端维修工程师只修通信、页面、状态、消息、恢复链；不改业务目标。
Supervisor / Watchdog自动接力看门人CodeBuddy 一轮结束或卡住时，负责自动唤醒/重启控制流程。
不要混淆：真正有权决定“下一步业务做什么”的只有决策端。

RC2.2 文件包里每个文件是干什么的

RC2.2 比早期版本多出一些文件，但这些文件并不代表新增了很多 AI。多数是规则、审计和归档资料。

第一次使用前：准备电脑、文件夹和备份

正式项目之前先准备三类目录：ClosedLoop 文件包目录、可丢弃测试工作区、独立状态文件夹。

  • 重要原始数据先备份。
  • 第一次只给 CodeBuddy 打开真正需要处理的目录，不要直接开放整个系统盘。
  • 状态文件夹不要放进要保护的原始项目目录。
  • 电脑不要设置成几分钟就自动睡眠。
  • 同一个项目不要同时开两个“决策端”主页面或两个“修复端”主页面。
状态文件夹不要乱删：它相当于游戏存档，里面保存进度、检查点、恢复记录、消息和动作状态。

第一次安装 CodeBuddy：先做最低风险测试

  1. 安装并登录 CodeBuddy。
  2. 打开一个空的测试文件夹，不要直接打开正式项目。
  3. 放一个普通 test.txt，让 CodeBuddy 只读取内容。
  4. 让 CodeBuddy 新建 hello.txt，确认它真的能创建文件。
  5. 不要为了方便就无条件开放全盘删除、支付、发布等高风险权限。

配置 Playwright：让 CodeBuddy 能操作 ChatGPT 网页

Playwright 可以理解为“让 CodeBuddy 像人一样打开网页、看页面、点按钮、刷新页面”。

  1. 确认 CodeBuddy 能启动一个由它控制的浏览器。
  2. 打开 ChatGPT 登录页。
  3. 出现登录、验证码、2FA 时，由你本人完成。
  4. 让 CodeBuddy 读取页面上一小段普通文字，确认它不只是把浏览器打开了，而是真的能看页面。
页面规则：决策端保留一个主页面，修复端也保留一个主页面；不要同一角色重复开很多活动页面。

开始一个新项目前，要打开哪些窗口

窗口什么时候建立项目运行时是否长期保留
需求润色端项目开始时需求冻结后可以退出主流程
决策端需求包准备好后是，主闭环核心
异常修复端正式运行前是，平时待机
CodeBuddy正式运行前是，实际执行端
不要传错文件：总规范、审计报告、SHA256、JSON 等维护资料平时不要一股脑上传到决策端或修复端。

第一次完整启动一个项目：从头照着做

第 1 步：需求润色端

  1. 新开 ChatGPT 对话，上传需求润色端启动文档。
  2. 用普通话描述你想做什么。
  3. 按真实意愿确认关键路径、删除/覆盖权限、版本等问题。
  4. 拿到完整 Frozen Requirement Package。

第 2 步：决策端

  1. 新开 ChatGPT 对话，上传决策端启动文档。
  2. 把完整 Frozen Requirement Package 交给它。
  3. 等待它完成审核并拆分 Work Unit。

第 3 步：异常修复端

  1. 新开 ChatGPT 对话，上传修复端启动文档。
  2. 看到“待机”状态即可，不要给它正常业务任务。

第 4 步：复制两个网页地址

复制“决策端网址”和“修复端网址”。Ctrl+A=全选，Ctrl+C=复制，Ctrl+V=粘贴。

第 5 步：启动 CodeBuddy

  1. 打开 CodeBuddy 执行端 TXT。
  2. Ctrl+A 全选，Ctrl+C 复制。
  3. 粘贴到 CodeBuddy 聊天并发送。
  4. 按提示把决策端网址和修复端网址交给 CodeBuddy。

第 6 步：等待 Handshake / Control Setup

这一步通常不用理解，只要不要同时手工乱点。系统会检查能力、状态文件夹、单写保护、页面绑定等。

第 7 步：进入主闭环

决策端下发本轮指令 → CodeBuddy 执行 → CodeBuddy 验证 → 汇报真实结果 → 决策端审核 → 下发下一轮 → 持续循环
RC2.2 的重要变化：正常情况下，你不需要每轮手工输入“继续闭环执行”。

大型任务为什么允许很多轮

大项目最危险的不是轮次多，而是一次让 CodeBuddy 做太多，做到一半出问题以后谁也说不清已经做了什么。

一个 Work Unit = 一次明确授权 + 一次执行 + 一次 fresh verify + 一次结果汇报 + 一次决策端重新审核

10 轮、50 轮、100 轮都可以。真正重要的是每轮有边界、有结果、有检查点。

CodeBuddy complete 是什么意思？

它可能只表示当前一次 agent 工作结束，不代表项目完成。RC2.2 把“业务是否继续”和“当前 CodeBuddy 进程有没有结束”分开。

正常情况下：不要看到 complete 就马上输入“继续”，也不要马上把它交给修复端。系统应该自动续跑。

自动续跑和 Supervisor：用人话怎么理解

Supervisor 可以理解成“看门人”。它不做业务决策，只检查 CodeBuddy 这一轮结束以后项目是不是还 ACTIVE；如果还要继续，就把下一次 Controller Tick 再启动起来。

现实限制：规则写进文档，不代表你的 Windows/CodeBuddy 环境已经真实具备可靠 Supervisor。长时间无人值守前必须先做 Runtime Regression。

ChatGPT 网页出现奇怪状态时先不要乱点

情况 A：回复壳子已经出现，但正文是空的

这时后台可能已经生成了完整回复，只是网页没有正常显示。

不要：不要重复发送上一条消息，不要马上点“重新生成”。

正确方向：保存状态 → 刷新 → 重新加载 → 查历史 → 必要时隔一段时间再刷新 → 找到完整回复后校验。

情况 B：“消息发送超时，请重试”

超时不等于没发送。原消息可能已经提交，甚至回复可能已经存在。

不要：不要看到 Retry 就马上点。先 history audit，确认消息和回复到底是什么状态。

其它常见异常

现象默认处理
一直“正在思考”，但发送按钮恢复视为可能显示不同步，刷新并查历史。
一直“正在思考”，也像在生成看有没有真实正文/packet 进展，长时间无进展才刷新。
“正在思考”消失，但没有正文不能认为没有回复；刷新、重载、查历史。
“连接中断，正在等待完整回复”刷新 → 检查 → 等待 → 必要时再刷新。

当前 30 秒刷新只是测试默认值，不是死规定；真正重要的是有没有实际进展。

CodeBuddy 什么时候自己修，什么时候找修复端

L0：CodeBuddy 本地恢复
↓
L1：CodeBuddy 自动调用修复端
↓
L2：Emergency Continuation
↓
L3：Manual Recovery Bridge

L0 包括刷新、重新绑定、查历史、消息状态核对、Action reconciliation 等。

重要原则：如果 CodeBuddy 自己也无法判断“现在是不是安全”，不应该问用户猜，而应把“不确定”本身作为 Repair 触发条件。

修复端到底负责什么

修复端可以做修复端不能做
判断网页/浏览器/消息/状态哪里坏了修改项目业务目标
告诉 CodeBuddy 如何安全刷新、重绑、核对消息自己制定新的业务技术路线
处理 unknown message、页面绑定、ledger 等控制问题跳过决策端直接给 CodeBuddy 新业务 Work Unit
确认什么时候可以安全回主闭环宣布项目最终业务 PASS

修复端一次没修好，会不会无限循环

不会。只有“有真实进展”的 Repair 才继续。

例如：页面从“绑定不确定”变成“绑定正常”，未知消息从 1 条变成 0 条，这算进展。

连续无进展：不能无限重复刷新。应升级到 Emergency Continuation，优先保住已经完成的成果。

人工测试：这是正常暂停，不是闭环坏了

有些项目必须由人亲自看、亲自体验或亲自操作。决策端必须给完整测试方案，而不是只说“请测试一下”。

测试编号测试内容操作步骤预期结果实际结果是否通过异常说明
T01示例：启动程序1. 打开程序
2. 等待进入主界面		正常进入且不崩溃

人工测试期间 CodeBuddy 应进入 WAITING_FOR_MANUAL_TEST_RESULT，保存状态，不继续修改被测对象。

你提交测试结果 → CodeBuddy 保存并结构检查 → 原样转交决策端 → 决策端决定通过 / 修复 / 补测 / 完成

人工恢复桥：什么时候需要你搬运信息

只有自动链路本身也传不动故障信息时，才使用人工恢复桥。

  • 登录彻底失效
  • CAPTCHA / 2FA
  • 电脑重启后自动控制器没恢复
  • 网络长期断开后恢复联网但没有自动接上
  • 第三方服务长期不可用
  • 不可观测的非幂等外部操作

你只负责：观察、复制、描述、身份验证、搬运信息。

你不负责：判断从哪一步继续、重发上一轮、重做业务动作、判断协议状态。

电脑重启、长期断网、第三方服务不可用时怎么做

电脑重启

  1. 重新打开 CodeBuddy 和浏览器，但先不要执行业务命令。
  2. 不要输入“从头再来”或“继续上一轮”。
  3. 优先让系统读取 Durable State 和 Recovery Capsule。
  4. 自动恢复没开始时，再用人工恢复桥。

网络长期断开

断网时冻结业务，不要离线重复执行。恢复网络后再重新绑定；自动恢复失败再用人工恢复桥。

第三方服务不可用

Repair 不能把对方网站“修上线”，只能保存 checkpoint、阻止重复提交并等待外部服务恢复。

不可观测的非幂等操作

绝对不要“再做一次试试”。例如支付、发布、外部提交在中断瞬间到底成功没有且无法查询时，必须保持 UNKNOWN_AFTER_INTERRUPTION。

Recovery Capsule：大型项目的恢复存档

Recovery Capsule 可以理解成“可恢复存档”。每个已经被决策端接受的 Work Unit 都应该留下恢复锚点。

它帮助系统知道：当前 Requirement 是哪个版本、最后哪个 Decision 和 Result 已确认、最新安全 checkpoint 在哪里、证据索引在哪里、还有没有未知 Action 或未知 Message。

你要做什么：日常不用打开 Recovery Capsule；只要不要手工删除状态目录。

想让项目连续跑几小时或几天，先看这里

需要的能力人话解释没有它会怎样
Runtime-native continuation 或 Supervisor一轮结束后能自动启动下一 Controller Tick。半夜一轮结束后可能停住。
Durable State进度真正落到硬盘，不只靠聊天记忆。重启后容易不知道做到哪。
Atomic Lease / Fencing同一时间只让一个控制器真正写。两个实例可能重复动作。
Recovery Capsule每轮都有恢复锚点。中断后沉没成本更大。
真实恢复演练故意中断一次，确认能安全恢复。纸面上安全，实际可能恢复不了。
当前现实状态：RC2.2/CP1 仍处于测试阶段，真正无人值守能力必须由真实 Runtime Regression 证明。

项目什么时候才算真的完成

不是 CodeBuddy 说 complete 就算完成，也不是某一轮 SUCCESS 就算完成。

只有决策端经过最终完成检查，确认所有要求、结果、恢复请求、未知 Action/Message 都已经收敛，才能宣布项目完成。

最后人工抽查：确认最终文件真的存在、能打开、内容符合需求。

小白版“绝对不要做”清单

  • 不要看到页面卡住就重复发送同一条消息。
  • 不要看到“消息发送超时”就马上点 Retry。
  • 不要看到 CodeBuddy complete 就手工输入“继续闭环执行”。
  • 不要因为命令报错就从头重跑整个 Work Unit。
  • 不要同时打开两个相同角色的 Decision 或 Repair 主页面。
  • 不要自己修改 MESSAGE_ID、DECISION_ID、ROUND_ID 等机器字段。
  • 不要删除 Control State、Recovery Capsule、Evidence、Ledger。
  • 不要把修复端当第二个决策端。
  • 不要混用不同版本的运行文档。
  • 不要在不知道外部动作是否成功时自动再做一次不可重复操作。

11. 按提示把两个网址发给 CodeBuddy。
12. 等系统完成 Handshake / Control Setup。
13. 之后进入：Decision → CodeBuddy → Verify → Result → Decision。

【正常运行】
14. 不需要每轮输入“继续”。
15. CodeBuddy complete 不等于项目完成。
16. 网页小故障先让 CodeBuddy 自动恢复。
17. L0 恢复无进展才自动进入 Repair。
18. Repair 连续无进展才升级 Emergency Continuation。

【人工测试】
19. 决策端给完整测试表 → 你按步骤测试 → 把结果交 CodeBuddy → CodeBuddy 转交决策端。

【自动链彻底断了】
20. 不重发、不重做 → 复制 CodeBuddy 最后内容 + 真实情况 → 人工恢复桥 → Repair。

【最终完成】
21. 只有 DecisionLayer 最终裁定 PROJECT_COMPLETE 后才算完成。

文件完整性和版本

同一个项目尽量全部使用同一套版本文件，不要把旧版 CodeBuddy 指令和新版 Decision/Repair 混着用。

SHA256：可以理解成“文件指纹”。平时不用管，只有怀疑下载文件损坏或被改过时才对比。
静态关键字审计 JSON：给协议维护者看的机器检查结果，普通用户可以完全不打开。

最后再记住这 7 句话

  1. 项目正常时：决策端决定，CodeBuddy 执行。
  2. 大型任务可以很多轮；每轮都要执行、验证、汇报、再等下一 Decision。
  3. 正常情况下不要手工输入“继续闭环执行”。
  4. 网页显示异常时先恢复页面和消息状态，不要重复发送。
  5. 修复端只修闭环，不负责业务决策。
  6. 自动链也断了时，你只负责观察、复制、描述、身份验证和搬运信息。
  7. 真正的“项目完成”只能由决策端最终裁定。
只记一句：不知道怎么办时，不要猜、不要重复、不要从头重跑。保留现场，让系统或修复端先判断当前状态。

RC2.2-CP1 最新收口提示

这部分来自 RC2.2-CP1 的增量说明，用来补充当前测试阶段的关键边界。

  • 自动续跑能力不够时，项目不应该正式开始。如果系统检查不到自动续跑或 Supervisor 已真实可用，应在启动门禁直接 BLOCKED，而不是先跑一轮再让用户继续。
  • 人工恢复桥重复发送时不要改内容。同一恢复桥应保持同一个身份和内容，不要修改几个字后反复发送。
  • 登录/验证码期间 Supervisor 应真正等人。不能把人工等待误判为卡死。
  • 人的记忆和系统记录冲突时，不要自己选。应保留现场交给 Repair/DecisionLayer。
  • 第三方服务不可用或不可重复动作状态不明时，不要“再做一次试试”。
状态：RC2.2-CP1 仍是 Paper/Runtime Regression 阶段，不代表生产冻结。
